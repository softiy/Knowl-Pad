## 2. Gitee 侧（**首次给出的路径有误，此处为更正版**）

### 2.1 正确入口

> ❌ 此前写的「仓库 → 管理 → 分支设置 → 保护分支」**并不存在**，故在网页上找不到。经查 Gitee 帮助中心（社区版文档
> `help.gitee.com/repository/branch/protected-branches`），正确位置为：

**方式一（最快）**：仓库 → **「代码」** → 左侧 **「分支」** → 找到 `main` 行 → 把「分支状态」由「常规分支」改为 **「保护分支」**。

**方式二（可自定义规则）**：仓库 → **「管理」** → **「保护分支设置」** → **「新建规则」** → 填分支名 `main`（或通配符）→ 配置推送/合并权限 → 保存；
⚠️ **然后必须回到「分支」页把 `main` 的状态设为「保护分支」**——官方文档明确：*「保护分支规则只影响状态是「保护分支」的分支，「常规分支」和「只读分支」都不影响」*。只建规则、不改状态 = 规则不生效。

### 2.2 ⚠️ 关键限制：默认规则**约束不到你自己**

Gitee 官方文档（企业版 `设置保护分支`）明确：

> 企业内的「超级管理员」「企业拥有者」「管理员」默认具备「推送代码」与「合并 Pull Request」权限，**依然可以对保护分支进行合并/推送操作，而无需遵从保护分支规则**。

即：**保护分支的默认语义是"只有仓库管理员能推送"**——个人仓库里管理员就是你本人，因此**默认规则不会阻止你直推 `main`**，它的价值在于约束未来的协作者。

**要真正约束到自己**，需在「保护分支设置」的规则里把推送权限选为 **「禁止任何人推送」**（可同时开启**评审模式**：无权限的推送会被自动转成一个 Pull Request，而不是直接失败）。这是 Gitee 侧最接近 GitHub `enforce_admins` 的做法。

### 2.3 可选的更彻底方案：让 Gitee 只做只读镜像

Gitee 提供「仓库镜像管理」（仓库 → 管理 → 仓库镜像管理），其中 **Pull 方向**可让 Gitee **自动从 GitHub 同步**（分支/标签/提交）。
若该功能当前仍可用，则可以把 Gitee 变成**纯拉取镜像**，从此**完全不需要向 Gitee 推送**，直推问题自然消失。

> ⚠️ 但该帮助页标注「**限时开放至 2022 年 08 月 31 日**，届时将更新产品策略」，**当前是否仍可用未经验证**——需在网页「管理」里确认是否有「仓库镜像管理」入口。若无此入口，则维持现状：**GitHub 合并后由本地推送同步到 Gitee**（当前做法，见 §4 记录）。

### 2.4 定位说明

Gitee 是**分发与镜像**渠道（Release 与 updater 源），开发与 CI 以 GitHub 为准。因此 Gitee 侧保护属**加固项**，
不阻塞开发；真正强制的"禁止直推 + CI 全绿"由 GitHub 分支保护承担（§1）。

## 3. 标准开发流程

```bash
git switch -c feat/<简短描述>     # 分支前缀：feat/ fix/ chore/ docs/ refactor/
# 改动 + 本地 pnpm ci 全绿
git commit -m "feat(scope): 说明"  # Conventional Commits（PRD CODE-09）
git push -u origin HEAD           # 推分支（推 main 会被拒绝）
# 在 GitHub 开 PR（自动带 .github/pull_request_template.md 的清单）
# CI 全绿 → 合并 → 删除分支
```

## 5. 紧急处置（如需绕过保护）

仅在 CI 自身故障、必须推送修复时使用，用完立刻恢复：

1. **推荐**：网页临时把 `enforce_admins` 或必需检查关掉 → 推送修复 → **立即恢复**；
2. 或经 API：`DELETE /repos/softiy/Knowl-Pad/branches/main/protection`（会清空全部设置，不推荐——恢复成本高）。

> 注意：`enforce_admins` 开启后，**管理员也无法直推**；若忘记恢复流程，日常改动一律走 PR 即可。
