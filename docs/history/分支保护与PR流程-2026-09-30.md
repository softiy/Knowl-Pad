## 1. GitHub `main` 分支保护（已启用）

通过 API `PUT /repos/softiy/Knowl-Pad/branches/main/protection` 设置，实测返回 200 并复核通过：

| 设置 | 值 | 说明 |
| --- | --- | --- |
| 必需 PR | ✅ 开启（批准数 **0**） | 强制走 PR；**0 批准**是为单人开发留出合并通路——GitHub 不允许自我批准，若设 1 则无人能合并。有第二位协作者后应改为 1 |
| 必需状态检查 | `17 项门禁（与本地同一脚本）`、`Windows 冒烟（构建 + 单元测试）` | 即 `ci.yml` 的两个 job；**未加入** `platform-smoke.yml` 的三个 job——该工作流带 `paths-ignore`，纯文档 PR 不会产生这些检查，加入会导致永久阻塞 |
| `strict`（分支必须最新） | ✅ | 合并前需与 `main` 同步，避免"通过了旧基线的 CI" |
| 禁止强推 / 禁止删除 | ✅ | |
| `enforce_admins` | ✅ **开启** | 管理员同样不能直推 `main`——这正是"禁止直接推送"的强制手段 |
| 必需对话解决 / 线性历史 | ❌ 未开启 | 当前单人开发，暂不需要 |

> `ci.yml` 已同时监听 `push` 与 `pull_request`，因此 PR 上会产生这两个必需检查，**不存在"必需检查永远等不到结果"的死锁**。

## 2. Gitee 侧

Gitee OpenAPI v5 **未暴露**分支保护接口（`/protected_branches` 返回 404，`/branches/main` 仅返回分支信息），需**在网页手动设置**：

> 仓库 → 管理 → 分支设置 → 保护分支 → 选择 `main` → 勾选「禁止直接 Push」/「Pull Request 合并」→ 保存

定位说明：Gitee 是**分发与镜像**渠道（Release 与 updater 源），开发与 CI 以 GitHub 为准；Gitee 侧保护属加固项，不阻塞开发。

## 3. 标准开发流程

```bash
git switch -c feat/<简短描述>     # 分支前缀：feat/ fix/ chore/ docs/ refactor/
# 改动 + 本地 pnpm ci 全绿
git commit -m "feat(scope): 说明"  # Conventional Commits（PRD CODE-09）
git push -u origin HEAD           # 推分支（推 main 会被拒绝）
# 在 GitHub 开 PR（自动带 .github/pull_request_template.md 的清单）
# CI 全绿 → 合并 → 删除分支
```

## 5. 紧急处置（如需绕过保护）

仅在 CI 自身故障、必须推送修复时使用，用完立刻恢复：

1. **推荐**：网页临时把 `enforce_admins` 或必需检查关掉 → 推送修复 → **立即恢复**；
2. 或经 API：`DELETE /repos/softiy/Knowl-Pad/branches/main/protection`（会清空全部设置，不推荐——恢复成本高）。

> 注意：`enforce_admins` 开启后，**管理员也无法直推**；若忘记恢复流程，日常改动一律走 PR 即可。
