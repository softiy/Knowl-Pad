### 5.3 `ready` 语义的排查记录（2026-10-08）

M3 复核 M3-8 指出 `IndexStatus.ready` **恒为 true**。查证与结论：

| 步骤 | 事实 |
| --- | --- |
| 定位 | `commands/vault.rs`：无库分支写 `ready: false`，**有库分支无条件写 `ready: true`** |
| 第一次尝试 | 判据取"meta 里有 `index_signature` 或 `built_at`" |
| **被测试推翻** | 新建索引库并 `open()` 后，**至少一个 meta 已存在** —— 因为 `write_meta` 在**开库路径**也会被调用（`storage/index.rs` 与 `index_rebuild.rs` 各有一条写入口） |
| 结论 | **"meta 存在"不等于"索引已建立"**，该判据不成立；改动已回退（不留猜测代码） |
| **机制已确认** | `storage::index::ensure_index_db` **已经算出** `RebuildOutcome`（`Fresh` / `Rebuilt { reason }` / 未变）并按结果打日志；随后 `DbPool::open_with` 里的 `bootstrap` **无条件**调用 `write_meta` —— 所以"库一被打开就有 meta"是**设计如此**，不是 bug。判据被推翻的机制就此坐实 |
| 下一步 | **把它从存储层显式返回**：`ensure_index_db` 的返回值带上 `RebuildOutcome`（或写进 `AppState` 的索引可信标记），`index_status` 据此填 `ready`；`Fresh`/`Rebuilt` 下 `ready=true` **可以**接受（索引确实建立过），`false` 应留给"从未建立且当前不可用" |（开库时已经算出 —— 日志里可见「索引库已丢弃重建…reason=…」），应把它从存储层**显式返回**，再由 `index_status` 据此填 `ready` |
