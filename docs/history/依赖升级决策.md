# 开发工具链大版本升级决策（M0）

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-09-25 |
| 背景 | 技术方案附录 D.3 第 5 项：一批 devDependencies 落后上游 1~3 个主版本 |
| 现状 | 全部 16 项门禁在**当前声明范围**下通过（`node scripts/run-gates.mjs`） |
| 策略依据 | 技术方案 §3.6.1：升级是**显式动作**，lockfile 变更单独成 commit |

## 决策

**M0 保持当前已测通的声明范围**，把大版本升级收拢为 M1 的独立任务。理由：M0 的目标是
「能否开工 + 门禁可信」，此时引入 ESLint 10 / Vitest 5 的配置破坏性变更会与脚手架验证混在一起，
出问题无法区分是"代码错"还是"工具错"。

## 执行约定（M1 启动时）

1. 一次只升一组（ESLint 组 / Vitest 组 / jsdom 组），每组单独 commit，**lockfile 变更不与其他改动混提**。
2. 每组升级后必须跑 `node scripts/run-gates.mjs` 全绿再合并；jsdom 组额外复跑 AC-SEC-01。
3. 若某组出现无法在 1 天内解决的配置问题，回退该组并登记新的 `DEBT`，不带病合入。
