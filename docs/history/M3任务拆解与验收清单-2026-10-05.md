## 1. M3 目标与 DoD（权威出处：PRD §9.1）

| 项 | 内容 |
| --- | --- |
| 名称 | **M3 解析与索引引擎** |
| 目标 | 知识网络的数据基础 |
| 主要交付 | Markdown 解析器（§3.1 **全部规则**）；jieba 分词；FTS5；全量/增量索引；文件监听；索引签名 |

### DoD 的展开（本计划的口径）

- **附录 B 的 25 条用例（B-01~B-25）**：准确率 ≥ 99% ⇒ 25 × 0.99 = 24.75 ⇒ **必须 25/25 全过**（24/25 = 96% 不达标）。
- **AC-SEARCH-01**：10000 篇夹具中 3 篇含「知识图谱的力导向布局」，搜「力导向布局」→ 3 篇全中且在前列、片段高亮、**< 200ms**。
- **AC-SEARCH-04**：`A.md` 中 `foo` 改 `bar` 保存后 **2 秒内**搜索一致，且无需手动重建。
- **AC-REL-03**：删除整个 `.knowlpad/` 后重建，链接数/标签树与计数/标题数/任意 100 个查询的结果集**逐项一致**；需覆盖「回收站为空」与「回收站非空」两种前提。

## 3. 工作包拆解（按依赖排序；交付行为**对账基准**，收尾时逐条核对）

### WP1 契约补齐与命令层测试床（**先做**，为后续所有命令兜底）

**交付**：
1. **DEBT-14 兑现**：Rust 命令层运行时测试床（`tauri::test::mock_app` 或把命令体抽成可注入状态的 service 函数），并把覆盖面接入门禁；
2. 索引域 4 命令契约：`index_rebuild { force }`、`index_cancel`、`index_signature_get`、`index_stats`（返回形状按 **D-18** 补进 PRD §5.3.7）；
3. 搜索域 6 命令契约：`search_fulltext`、`search_quick_open`、`search_in_file`、`replace_in_file`、`search_history_get`、`search_history_clear`（形状补进 PRD §5.3.4）；
4. 前端封装同步（`core/ipc/commands.ts`）+ 事件载荷类型（`core/ipc/events.ts`，见 WP6）。

### WP2 Markdown 解析器（§3.1 全部规则）

**交付**：
1. 解析器落在 **`crates/kp-domain`**（纯函数、无 IO、可高覆盖测试）：`md_parse` 模块 + `ParsedNote` 结构（链接/嵌入/标签/标题层级/块 ID/frontmatter 别名）；
2. §3.1 规则逐条实现（wikilink 形态与转义、代码区不解析、标签层级与数字开头、frontmatter（含 YAML 错误降级）、块 ID、Setext 标题…）；
3. **附录 B 的 25 条用例夹具入库** `tests/fixtures/parser/B-xx.md` + `expected.json`（按附录 B 的固化流程：期望值**由 §3.1 条款推导**，不抓取任何外部软件行为）；
4. 链接**只提取不裁决**（resolved/dangling/ambiguous 的裁决归 M4），但结构上要为 M4 留好字段；
5. CRLF/BOM 保持（NFR-PLAT-05/06）。

### WP3 分词与 FTS 管线

**交付**：
1. 引入 `jieba-rs`（版本与词典策略见 §5 口径 6），产出**预分词文本**写入 `note_fts`（unicode61 之上叠加预分词，兼顾中英文）；
2. `tokenizer_version` 与 `tokenizer_dict_hash` 写入签名（词典变化 ⇒ 签名变化 ⇒ 自动重建）；
3. FTS 查询构造（短语、前缀、`-` 排除），为 M5 的高级语法留出 AST 位置；
4. 中文短语命中：AC-SEARCH-01 的「力导向布局」必须命中（否则 unicode61 只能按单字命中）。

### WP4 全量索引引擎

**交付**：
1. 遍历（跳过 `.knowlpad`/`.obsidian`/`.git` 与 `NEVER_TOUCH_DIRS`）→ 解析 → 批量事务写入（`file`/`heading`/`block_id`/`link`/`tag`/`file_tag`/`file_alias`/`note_fts`）；
2. 批处理与事务边界（技术方案约定）、失败可续、单文件失败不中断整库；
3. **进度上报与取消**（`kp://index/progress` + `index_cancel`）→ FR-VAULT-09（> 5000 文件显示进度、可取消）；
4. `index_rebuild { force }` 走既有 §4.4 的文件级重建切换；
5. `index_stats` 提供实体计数（设置页用）。

### WP5 增量索引与文件监听

**交付**：
1. 引入 `notify` + `notify-debouncer-full`（技术方案 §3.5.2 的版本矩阵）；
2. 变更事件 → 解析 → 事务内增量更新（含删除与重命名的实体清理）；
3. **AC-SEARCH-04**：保存后 2 秒内可搜到新内容、旧内容不再命中；
4. Watcher 的防抖与自写回环抑制（自己写入引发的 fs 事件不得触发重复索引）；
5. 与编辑器的自动保存协同（M2 的 `note_write` 成功后主动通知索引，避免等待 fs 事件）。

### WP6 事件通道（`kp://fs/*` 与 `kp://index/*`）

**交付**：
1. Rust 侧统一 `emit`（`kp://fs/created|modified|removed|renamed`、`kp://index/progress|completed|failed|rebuild-required`）；
2. 前端 `core/ipc/events.ts` 类型化 `listen` 封装（**唯一**允许 `listen` 的地方，与 SEC/FE-04 的 invoke 约束对称）；
3. 状态栏接**真实**信号：`index/progress` → 「索引中（x/y）」、`index/failed` → 「索引失败」（替换 M2 的近似判定）；
4. 事件载荷按 PRD §5.4 定义（不新增字段，缺字段则登记勘误）。

### WP7 文件树数据源切换与过滤

**交付**：
1. 文件树由「直接读盘」切到**索引数据源**（FR-STORAGE-04：`.knowlpad` **永不**出现在树/搜索/图谱/标签统计）；
2. 索引不可用时回退直读（保证 NFR-PERF-02 的「打开即可用」）；
3. FR-FILE-02 的排序选项（按修改时间/类型）随数据源一并落地（**DEBT-19 的一部分**）；
4. **AC-FILE-06 的真机度量**：真实 WebView 下的帧率/内存/200ms 渲染（补 M2 的近似口径）。

### WP8 质量与门禁补强（**DEBT-21**）

**交付**：
1. 门禁 17 增强：校验**参数/返回形状**（不只命令名）+ 覆盖事件名；

### WP9 存储面遗留

## 7. 风险与依赖

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| jieba 词典与内存占用 | 大 Vault 下索引变慢/占内存 | 词典一次加载复用；签名含词典 hash；NFR-PERF-03 三档度量把关 |
| 10000 篇夹具的 CI 成本 | 门禁变慢、误报回退 | 分档：标准档必跑、大档按门禁/缓存跑（§5 口径 7） |
| `notify` 跨平台差异（Windows/macOS/Linux） | 事件丢失或重复 | 防抖 + 自写抑制 + 「保存后主动通知索引」双保险；三平台冒烟按 CI 现状 |
| 索引期间的用户写入 | 竞态导致内容被旧索引覆盖 | 索引只读文件内容、不写用户文件；写入与索引各自独立事务；用 `mtime` 与签名判断新鲜度 |
| FTS5 + 预分词的组合 | 命中率不达标（AC-SEARCH-01） | WP3 先做小样本验证再全量；把「短语命中」作为该 WP 的准入门槛 |
| 事件洪泛 | 前端卡顿 | 进度事件按节流上报（≥ 100ms 间隔）；`fs/*` 事件只在索引相关变更时发 |
| 依赖引入（jieba-rs/notify/walkdir/uuid/dashmap） | 与矩阵不一致（M1 复核已发现"引入阶段"漂移） | 逐个按 §3.5.2 矩阵版本引入并**同步矩阵的引入阶段列**（DEBT-24 的同类问题） |
