### WP2 Markdown 解析器（§3.1 全部规则）

**交付**：
1. 解析器落在 **`crates/kp-domain`**（纯函数、无 IO、可高覆盖测试）：`md_parse` 模块 + `ParsedNote` 结构（链接/嵌入/标签/标题层级/块 ID/frontmatter 别名）；
2. §3.1 规则逐条实现（wikilink 形态与转义、代码区不解析、标签层级与数字开头、frontmatter（含 YAML 错误降级）、块 ID、Setext 标题…）；
3. **附录 B 的 25 条用例夹具入库** `tests/fixtures/syntax-compat/` + 结构化 `expected.json`（**路径与形态以技术方案 TECH:3152 为准**；期望值按附录 B 的固化流程**由 §3.1 条款推导**，不抓取任何外部软件行为）；
4. **链接裁决的归属（v2 修正）**：MD-WL-03 明确「解析阶段一律不判定有效性，由**索引阶段**统一裁决」，技术方案的全量索引流程也把「链接裁决」列为第 ⑤ 步（`domain/index_engine/link_resolve.rs`）→ **resolved/dangling/ambiguous 属 M3 的索引阶段**；M4 承接的是**反链/悬空/歧义面板与链接改写**（PRD §9.1 的 M4 行把"裁决"写在 M4，与本条冲突 → 见 §5 口径 9）；
5. 实现约束（技术方案）：**正则必须用 `regex`（线性时间，免疫 ReDoS，SEC-03）**；span 用字节偏移；解析失败**永不抛错**（返回 `ParsedNote` 而非 `Result`）；单文件解析 **10s 超时**（超时跳过 + warning）；> 5MB 的 note 跳过 + warning（SEC-11）；
6. 解析器落 **目录** `domain/md_parse/{mod,frontmatter,wikilink,tag,heading,block_id,code_fence}.rs`（PRD 写单文件 `md_parse.rs`、技术方案写目录 → 以技术方案为准，见 §5 口径 10）；
7. CRLF/BOM 保持（NFR-PLAT-05/06）。

### WP3 分词与 FTS 管线

**交付**：
0. 依赖按矩阵引入：`jieba-rs 0.11.0`、`yaml-rust2 0.13.0`（frontmatter）、`regex 1.13.1`（wikilink/搜索语法）——三者引入阶段均为 M3（技术方案 §3.5.2）；同时**同步该表的「引入阶段」列**（M1 复核发现 notify/walkdir/uuid/dashmap 的行与现实不符）；
1. 引入 `jieba-rs`（版本与词典策略见 §5 口径 6），产出**预分词文本**写入 `note_fts`（unicode61 之上叠加预分词，兼顾中英文）；索引侧 `cut(text, false)`（**非 HMM**：HMM 概率输出会破坏 AC-REL-03 的重建一致性）；查询侧同样先分词再构造 MATCH（**FTS5 的 NOT 是二元运算符**，多排除词用链式 `expr NOT a NOT b`）；
1b. **`escape_fts` 必须处理** `" * ^ : ( ) - +`；**高亮不得用 `snippet()`**（它作用于分词后文本、会带空格）→ 取命中 rowid → 读原文 → 原文定位 → 截 ±N 窗口（FTS-04 / FR-SEARCH-04）；
1c. `tokenizer_dict_hash`：jieba 词典编译期内嵌，运行时无独立文件可哈希 → **由 `build.rs` 用 `include_bytes!` 对词典资源算 SHA-256 前 16 位**（叠加 crate 版本与 features），写入签名；
2. `tokenizer_version` 与 `tokenizer_dict_hash` 写入签名（词典变化 ⇒ 签名变化 ⇒ 自动重建）；
3. FTS 查询构造（短语、前缀、`-` 排除），为 M5 的高级语法留出 AST 位置；
4. 中文短语命中：AC-SEARCH-01 的「力导向布局」必须命中（否则 unicode61 只能按单字命中）。

### WP4 全量索引引擎

**交付**：
1. 遍历（跳过 `.knowlpad`/`.obsidian`/`.git` 与 `NEVER_TOUCH_DIRS`）→ 解析 → 批量事务写入（`file`/`heading`/`block_id`/`link`/`tag`/`file_tag`/`file_alias`/`note_fts`）；
2. 批处理与事务边界（技术方案约定）、失败可续、单文件失败不中断整库；
3. **进度上报与取消**（`kp://index/progress` + `index_cancel`）→ FR-VAULT-09（> 5000 文件显示进度、可取消）；
4. `index_rebuild { force }` 走既有 §4.4 的文件级重建切换；
5. `index_stats` 提供实体计数（设置页用）；
6. **DEBT-04 实测**：链接裁决用 `TEMP TABLE link_candidates` 做全局裁决，**10 万文件规模下是否超 NFR-PERF-03 的 8min 预算必须实测**；超出则改分批 + 函数索引 `lower(stem)`；
7. **遍历与监听必须复用同一份忽略规则**（`IGNORED_DIRS = [".knowlpad", ".obsidian", ".git", "node_modules"]` + `.kp-tmp-*`）——技术方案 TECH:1752-1754 明确这是防「索引风暴/索引遗漏」的单一真相源；每次打开 Vault 另做一次 **mtime 对账扫描**兜底监听遗漏。

### WP5 增量索引与文件监听

**交付**：
1. 引入 `notify` + `notify-debouncer-full`（技术方案 §3.5.2 的版本矩阵）；
2. 变更事件 → 解析 → 事务内增量更新（含删除与重命名的实体清理）；
3. **AC-SEARCH-04**：保存后 2 秒内可搜到新内容、旧内容不再命中；
4. Watcher 的防抖与自写回环抑制（自己写入引发的 fs 事件不得触发重复索引）；
5. 与编辑器的自动保存协同（M2 的 `note_write` 成功后主动通知索引，避免等待 fs 事件）；
6. **监听死循环防护**（技术方案 TECH:1778 列为最高优先级，且是 TECH:4087 的 M3 验证项 ③）：索引库写入落在 `.knowlpad/` 内，若不过滤会形成「索引写入 → 监听 → 再索引」的无限循环 → **必须有针对性测试**（索引进行中人为修改 Vault 内文件，断言不产生循环）；
7. **平台差异与降级**（验证项 ④）：Windows `ReadDirectoryChangesW` 缓冲溢出报 Rescan → 触发全量 mtime 对账；macOS FSEvents ~1s 延迟且可能重复投递 → 200ms 去抖 + pending 去重；Linux `inotify` 的 `max_user_watches` 默认 8192 → 捕获 `MaxFilesWatch` → 上报（含 sysctl 建议）并**降级为每 5s 轮询 mtime**。
