**📌 教训（2026-10-16，PR-B）：写"改写用户文件"的代码时，三件事必须靠用例钉住。** 三条都是本轮真实踩到的：

1. **同一源位置可能被解析器给出多条条目**：层级标签 @@#old/name@@ 会同时产出"祖先条目 @@old@@"与"自身条目 @@old/name@@"，
   两者是**同一个 line/col**、但名字长度不同。按 (line, col, len) 去重**去不掉**它们 ⇒ 同一段文本被替换两次，
   第二次用的是**旧列偏移**（一次替换后列已偏移）⇒ 轻则重复计数，重则**改坏文件内容**。
   口径：**按源位置去重、保留最长者**（"一个源位置 = 一处"）。
2. **不是所有标签都有行列号**：MD-TAG-06 规定 frontmatter 的标签 @@line = -1@@（无行列号）。
   只按行列号改写 ⇒ **只有 frontmatter 的标签的文件一处也不改**，而且被算成"没有命中"**静默**排除在计划外 ——
   用户以为改完了，实际那批文件原样躺在磁盘上。口径：**正文按解析器位置、frontmatter 按块扫**（先拿块的字节范围再在块内找 @@tags:@@）。
3. **断言不要用 @@contains@@ 做存在性检查**：早先那条 frontmatter 用例只断言 @@contains("new/name")@@，
   被**正文**那处命中"顺带"满足了 ⇒ 它一直在绿，却盖住了第 2 条真问题。
   口径：改写类断言一律**逐字节相等**（@@assert_eq!@@ 全文），不要用"含不含某串"代替。

> 检查清单（下次做同类改写时照着过）：① 同一位置会不会被给出多次？② 每条来源都有位置信息吗？
> ③ 我的断言能不能在"某一条来源完全没改"的情况下依然通过？
**📌 教训（2026-10-16，PR-A）：契约形状必须从实现实测转写，不能凭对验收原文的直觉推断。** 因果链（可复现）：

**天然已含全部子孙** ⇒ 再逐级相加是**重复计数**，该字段**必须删除**（两步的实测证据都在 PR-A 的提交里）。
⇒ 两条纪律：① **权威字段表要等"实现 + 真实夹具"跑过再定稿**（本轮走"先写形状、后按实测回写"，多跑了一轮）；② 验收原文里"计数/引用"这类词**先确认单位**（行数？篇数？），否则会写出一个自洽但与实现重复的字段。

**⚠️ 基准环境登记（2026-10-15，M5 批次 5 后续补登）**：PRD §6.1.1 规定性能指标的**最低基准环境**是「4 核 @ 2.5GHz / 8GB / SATA SSD」，并写明「低于此环境的机器不作为验收依据」；SJ-02 也要求「§6.1 全部性能指标在规定的基准环境下达标」。而**本节以上所有实测数字（含 `NFR-PERF-03` 首次索引的 **11573 ms**）都来自开发机，不是基准机** —— 核数、主频、磁盘类型均未按 §6.1.1 标定。因此：

- 这些数字只能回答「**当前实现处于什么量级、瓶颈在哪一阶段**」，**不能**用来判定达标与否；
- **不得**以"机器不对"为由放行，也**不得**据此放宽预算 —— 判据与预算一字未动（这是登记，不是豁免）；
- **判定以基准环境复测为准**。可执行的复测路径（同一份也写在 `perf/d25-budgets.json` 的顶层 `environment.how_to_rerun`）：
  1. 在基准环境生成夹具：`node scripts/gen-fixture-vault.mjs --tier standard --out <夹具目录>`
  2. 整轮采样与预算比对：`KP_D25_VAULT=<夹具目录> KP_D25_NOTES=3000 node scripts/perf-d25.mjs --tier standard`
  3. 只复测判定项（最快）：`KP_D25_VAULT=<夹具目录> KP_D25_NOTES=3000 cargo test -p knowl-pad --locked d25_nfr_perf_03_first_index -- --nocapture --test-threads=1`
  4. 复测分项（定位瓶颈阶段）：把上一条的用例名换成 `d25_nfr_perf_03_breakdown`
  5. 采样器写 `perf/d25-report.json`（已 gitignore）并逐条打印 已达标 / 超预算 / proxy / 待接入
- **报告必须同时记录机器规格**（核数 / 主频 / 磁盘类型），否则数字仍然不可比；
- 若基准机不可得：优先用与 §6.1.1 同档的 CI runner，并在报告中明确标注"非基准机，仅供参考"，**不得**当作判定结论。

**🔬 基准环境不可得时的可比方法（2026-10-15 新增）**：只"换台机器再跑一遍"是没用的 —— 两个数字不可比。做法是先跑**校准微基准**把机器差异压成两个标量，再做**有假设的换算**。

- 跑法（任意机器原样可跑，不需要夹具）：`cargo test -p knowl-pad --locked calib_ -- --nocapture --test-threads=1`
  - `D25 CALIB-cpu us_per_iter=…`：固定 2KB 级笔记上的「解析 + 分词」循环（与 `index_engine` 同形的两步纯 CPU 工作）＝**单核吞吐**；
  - `D25 CALIB-persist us_per_commit=… checkpoint_us=…`：与生产**同一套 PRAGMA**（WAL + synchronous=NORMAL + autocheckpoint=1000）下的**小事务提交**与 **WAL 检查点**延迟。
- **本机（开发机）2026-10-15 实测**：CPU **1897 µs/iter**（5 轮中位数，极差 1848–1987，±4%）；小事务提交 **24 µs**、4MB WAL 检查点 **753 µs**（732–977）；`journal_mode=wal`、`synchronous=NORMAL`（⇒ 小提交并不 fsync，磁盘成本集中在检查点）。
  机器档案：AMD Ryzen 7 8845HS（8 物理核 / 16 逻辑核 @3.8GHz）、64GB 内存、索引库所在卷 = **NVMe SSD**（ZHITAI TiPlus7100）。
- **换算模型**：总耗时 ≈ CPU 侧 ÷ c + 持久化侧 × d（c = 基准机单核吞吐 ÷ 本机；d = 基准机持久化延迟 ÷ 本机）。
  假设：**索引是单线程的 ⇒ 与核数无关**；解析/分词/扫描/派生表写入随单核吞吐缩放；分批 COMMIT 与检查点随持久化延迟缩放。
- 本机口径 11637 ms 的分解：**CPU 侧 11125 ms + 持久化侧 512 ms**（`txn_commit`，16 个 chunk）。据此换算：

  | 情景（基准机相对本机） | c | d | 预期总耗时 | 结论 |
  | --- | --- | --- | --- | --- |
  | 同档（仅作下界） | 1.00 | 1.00 | 11637 ms | 超 1637 ms |
  | 单核慢 20% / 磁盘慢 50% | 0.80 | 1.50 | 14674 ms | 超 4674 ms |
  | 单核慢 33% / 磁盘慢 100% | 0.67 | 2.00 | 17628 ms | 超 7628 ms |
  | 单核慢 40% / 磁盘慢 150% | 0.60 | 2.50 | 19822 ms | 超 9822 ms |
  | **单核快 20% / 磁盘快 20%** | 1.20 | 0.80 | 9680 ms | ✅ 达标（**唯一窗口**） |

- **盈亏平衡（可证伪条件）**：要进 10000 ms，基准机单核必须比本机**快约 17%**（d=1）或**快约 24%**（d=2）。
- **结论（三类之一）**：**在基准环境量级下预期仍超预算**。依据：本机已超 14%，而 PRD §6.1.1 的「4 核 @2.5GHz / SATA SSD」在单核吞吐与磁盘延迟上都不太可能比本机（8 核 3.8GHz / NVMe）快 17% 以上；**只有基准机确实更快时结论才翻转**。
- **它仍不是判定**：这是换算不是判定，**不得**据此放行、**不得**据此放宽预算；真正的判定以基准机（或 §6.1.1 同档机器）复测为准。
- **CI runner 作为第二个数据点（本任务未实测 ✗）**：本机没有 `gh` CLI，我无法触发 CI。可复制步骤：① 推分支；② GitHub → Actions → **CI** → *Run workflow*（`ci.yml` 已带 `workflow_dispatch`）→ 选该分支；③ 要在 CI 里拿到校准数字，在 Windows job 增加一步 `cargo test -p knowl-pad --locked calib_ -- --nocapture --test-threads=1`，并按 `how_to_rerun` 生成夹具后跑 `d25_nfr_perf_03_first_index`。
  注意：托管 runner 常见规格为 2 vCPU/7GB 或 4 vCPU/16GB（随套餐与仓库可见性而变），**都不是** §6.1.1 的基准机；其磁盘是网络/共享存储、I/O 抖动大 ⇒ **CPU 标量可比性较好，持久化标量只能作参考**。

**📌 教训（2026-10-15，性能归因）：归因必须有对照组，否则会把漂移当成收益。** 可复现的因果链：

1. 给索引写入加 `prepare_cached` 之后，`fts` 阶段**连续两轮**从 312/316 ms 降到 281/295 ms（−7%~−10%），
   看起来就是"缓存省下来的"；
2. 但补做同语句对照实验（`d25_nfr_perf_03_fts_write_breakdown`）后：**A 每次 `prepare_cached` 143.0 µs/行
   vs C 每次重新 prepare 143.1 µs/行（差 0.1%）**，B（完全无 prepare）135.5、F（批量 10 行/语句）136.0 µs/行
   ⇒ **该语句上 prepare 成本 ≈ 0**，"−7%~−10%" 因而**无法归因于缓存**，只能记为**运行间漂移**
   （或同事务内其它写入改变了页缓存/WAL 状态）；
3. 结论（已同步登记到 `perf/d25-budgets.json` 的 `NFR-PERF-03-first-index.scope`）：
   **"改了什么"与"数字变了"同时发生，不等于因果**。凡要写成"某优化带来 X% 收益"，必须同时具备
   ① 同语句/同操作的 **A/B/C 对照**（改前写法 vs 改后写法 vs 理论下界），② 同一轮里**未改动的对照阶段**
   （本次是 parse / resolve / tag，逐轮稳定）；
4. **附：本轮实验里我自己犯的两个"看起来合理但错"的错**（一并留痕，因为正是它们差点让错结论写进真源）：
   - ① **第一版每行 autocommit**（漏了显式事务）⇒ 量到的是"每行一次 fsync"的**提交**成本（449/288/321 µs/行），
     不是插入成本；把整批包进一个事务后才变成 143/135/143；
   - ② **第二版 `tiny` 开关没被使用**（被 clippy 的 unused variable 抓到）⇒ 变体 D 其实写的是同一段长文本，
     于是"成本与文本长度无关"的初判**是假的**；修好后 D 从 ~129 µs/行 掉到 **4.7 µs/行**，结论推翻重写。
   ⇒ 教训：**对照变体必须自证"它真的改了我以为它改的东西"**（本次靠编译告警 + 数量级异常才抓住）。
